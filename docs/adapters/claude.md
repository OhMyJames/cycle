# Claude 适配

状态:草稿。验证日期 2026-11-18。

`harness/claude`:把 Claude Agent SDK 包装成 ACP v2 agent,通过 stdio 与 daemon 通信。决策见 [0001](../decisions/0001-claude-acp-adapter.md)。

验证所用版本:`@anthropic-ai/claude-agent-sdk` 0.3.327,`@agentclientprotocol/sdk` 2.7.0,Bun 1.4.4。验证先用本地模拟的 Anthropic API,之后又用真实模型验证过(见文末)。

## 进程模型

一个 session 一个 Claude 进程(流式输入),空闲 5 分钟释放,取消用 `interrupt`,详见 [决策 0007](../decisions/0007-resident-claude-process.md)。真实模型:首个回合 2.7 秒,同一进程里的后续回合 1.5 秒。一个空闲的进程约 230 MB。

## 代码结构

分两层(CYCL-250):`src/agent.ts` 只管 ACP,读请求、回答;session、进程和 turn 的生命周期在 `src/lifecycle.ts`(`Lifecycle`:起进程、读它的输出、结束 turn、空闲释放、取消)。其余各自一个模块:`process.ts` 起一个 Claude 进程(输入队列和 `Options`),`session.ts` 是 session 和 turn 的状态,`events.ts` 处理 turn 之外的消息(压缩、命令、模式、任务、重试),`permissions.ts` 是权限卡和表单,`config-options.ts` 是模型、effort、权限模式的选项,`usage.ts` 是用量和套餐用量,`schedules.ts` 是定时调用(含 Stop hook)。子 agent(`subagents.ts`)和其他后台任务(`tasks.ts`)共用 `task-ledger.ts` 记哪些任务已告知、在哪一轮运行、离开清单和进程退出时怎样结束。

## 启动与配置

- 入口 `src/main.ts`。所有配置通过环境变量 `CYCLE_ADAPTER_CONFIG`(JSON)传入:`{ env, claudeExecutable? }`。
- `env` 是 Claude 进程能看到的**全部**环境,不继承适配进程自己的环境。由 daemon 按白名单填。
- 凭证、`CLAUDE_CONFIG_DIR`、`ANTHROPIC_BASE_URL` 等都在这里。适配进程不读宿主机的 `~/.claude`。
- 不设 `claudeExecutable` 时用 SDK 自带的二进制,不依赖机器上装了 `claude`。
- **配置来源**:不传 `settingSources`,所以 SDK 加载全部来源。用户级的来自 `CLAUDE_CONFIG_DIR`(daemon 给的是 `$CYCLE_HOME/claude`,Cycle 托管);项目级的(`CLAUDE.md`、`.claude/settings.json`、`.claude/settings.local.json`、`.mcp.json`、`.claude/skills`)照常从 `cwd` 加载。`claude mcp add --scope local` 加的服务器存在用户级的 `.claude.json` 里,所以在 `~/.claude` 里加的,Cycle 看不到;要跟着项目走,写在 `.mcp.json` 里。
- **plugin**(protocol.md §15,`src/plugins.ts`,CYCL-83):`ClaudePlugins` 运行 Claude 自己的命令行管理 plugin(`plugin list --available --json`、`marketplace list|add|remove|update --json`、`install|uninstall|enable|disable|update --scope user --json`),不读也不写 Claude 的 plugin 文件格式,只为统计"带了什么"数一遍已装 plugin 目录里的 `skills/`、`commands/`、`agents/`、`hooks/hooks.json`。从不带 `-y`、`--accept-command`:来源要先运行自己命令的那一类会失败,报 `needs_command`。用户输入的来源地址放在 `--` 之后(`--json` 必须在 `--` 之前,否则会被当成地址)。因为不传 `settingSources`,用户级启用的 plugin 由会话自己加载,适配里没有加载 plugin 的代码。会话里 plugin 的 MCP 服务器叫 `plugin:<plugin 名>:<服务器名>`;`session/new`、`session/resume` 的 `mcpServers` 里有同名条目时,Claude 用给的那个,不再访问 plugin 声明的地址(daemon 靠这一点把它换成网关地址)。2026-11-23 用 2.1.327 实测,集成测试 `adapter.integration.ts` 最后一条每次验证这个命名和顶替;升级 SDK 后它失败,就是这两点之一变了。没加任何来源时就有内置目录 `anthropic-plugin-directory`(约 3800 项,要联网)。
- **文件夹信任**(protocol.md §8 "信任文件夹"):Claude 只在信任过的文件夹里运行项目配置里的命令(`headersHelper`、hooks 等)。它把信任记在用户级的 `.claude.json` 里(`projects[路径].hasTrustDialogAccepted`),而在 SDK 里没有弹窗,也没有选项可传(0.3.327 的类型定义里没有)。所以适配在 `session/new`、`session/resume` 的 `_meta["cycle/trusted"]` 是 `true` 或 `false` 时,在启动 Claude 进程之前把它写进 `$CLAUDE_CONFIG_DIR/.claude.json`(没有 `CLAUDE_CONFIG_DIR` 时用 `$HOME/.claude.json`),路径用 `cwd`,`cwd` 的真实路径不同时两个都写;没带这个键时不动。值已经一样就不写;要写时先写临时文件再改名,文件读不了(不是 JSON)就不写,在 stderr 里说一声。Claude 进程自己也会改这个文件,两边同时写时可能有一方的改动丢失,所以只在值不同时写,写的是读到的整份加上这一项。2026-11-19 前没有这一步,Cycle 里 `headersHelper` 从不运行,带它的 http MCP 服务器一律显示为"需要登录"(Claude 的 MCP 日志:`headersHelper not run: this workspace has no persisted trust`)。

## 权限模式

取值是 SDK `PermissionMode` 的原值,不改名(存进配置和索引的就是它);给人看的名字和说明只在 `CLAUDE_PERMISSION_MODES`(`harness/claude/src/config-options.ts`)里写一次,ACP 的 `configOptions` 和 daemon 的 `configSchema`(`oneOf`)都从它生成。

| 值                  | 名字               | 说明(界面上显示的英文原文)                                                                                                     |
| ------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| `auto`(默认、推荐)  | Auto               | A model reviews each action and allows or denies it, and asks you when it cannot tell. Not every account has it.               |
| `default`           | Ask before acting  | Asks you before Claude edits a file or runs a command. Reading is allowed without asking.                                      |
| `acceptEdits`       | Accept edits       | Edits to files in the working folder are allowed without asking. Commands still ask.                                           |
| `plan`              | Plan mode          | Claude reads and writes a plan but changes nothing. It starts work only after you approve the plan.                            |
| `dontAsk`           | Don't ask          | Never asks. Any edit or command that settings have not already allowed is denied, so without allow rules Claude can only read. |
| `bypassPermissions` | Bypass permissions | Every edit and command runs without asking. Use only where Claude can do no harm, such as a sandbox.                           |

新 session 从 `auto` 起(`DEFAULT_PERMISSION_MODE`),它的选项带 `_meta["cycle/recommended"]`,列表里排第一。恢复一个没有记下 mode 的 session 时仍按 `default`:那是 auto 成为默认之前建的，当时就是先问再做，恢复不能把它放宽。daemon 从这次起会把新 session 的初始值记下(见协议 §10),所以以后的 session 恢复时按记下的值。

起进程时总是带 `allowDangerouslySkipPermissions: true`:它只允许这个模式,不打开它;不带的话,运行中切到 `bypassPermissions` 会被拒,进程被释放。为什么全部提供,见 [笔记](../../.agents/notes/2026-11-19-offer-every-claude-permission-mode.md)。

未验证:在没有 auto 的账号上显式传 `auto`,SDK 会怎样(猜测是退回 default 并经 `system/status` 报告,适配器会把它当成 `config_option_update` 转发;如果是报错，新 session 的第一个 prompt 就会失败。auto 是默认，所以这一点要先在真实账号上确认);`dontAsk` 和 `bypassPermissions` 只有单元测试(假的 query),没有在真实模型上跑过。

## 验证结果

`bun run test:integration`(在 `harness/claude` 下)把适配器作为独立进程启动,走真实的 SDK 和它自带的 Claude 二进制,对本地模拟 API 说话。`bun test` 和提交门禁不运行它。

| 问题                                                         | 结果                                                                                                                                                                                                                         |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SDK 的 `query()` 能在 Bun 下运行,且这台机器上没有 `node` 吗? | 能。SDK 自带二进制,不需要 Claude 登录,也不需要 `claude` 在 PATH 上                                                                                                                                                           |
| daemon 提议的 sessionId 会被采用吗?                          | 会。`session/new` 返回同一个 id,第二个进程用它恢复                                                                                                                                                                           |

| 适配器自己发 `user_message` 吗?                              | 发,用 `session/prompt` 返回的 `messageId`。所以 Claude 不需要 daemon 合成这一条(协议 §8)                                                                                                                                     |

## 观察到的行为

- Claude 对只读或安全的 Bash 命令(如 `echo`)不请求权限,所以测试用 `touch` 来触发审批。
- SDK 启动的 Claude 进程会在发给模型的用户消息里自己加 `<system-reminder>` 文本(比如 git 提交的署名说明)。这是 Claude Code 自己的行为,不是适配器加的。
- 取消时适配器无论 SDK 怎么结束都报 `cancelled`;"剩余文本没有到达"这条断言靠的是适配器不再转发,不能单独证明 Claude 进程已被终止(进程是否被终止没有断言)。

### 后台任务和 goal(CYCL-120,2026-11-22)

SDK 0.3.327(CLI 2.1.327),haiku,`harness/claude` 的 `test:real` 里两条用例,另用一个直接调 `query()` 的探针看 SDK 原样发出的消息。

- **后台命令**:`task_type` 是 `local_bash`。顺序是 `background_tasks_changed`(不带 `tool_use_id`),然后 `task_started`(带 `tool_use_id`、`is_backgrounded: true`);结束时 `task_updated`(`patch.status: "completed"`)、`task_notification`(`status: "completed"`),再来一份不含它的清单。
- **Monitor**:`task_type` 也是 `local_bash`,和后台命令无法从任务本身区分(CLI 内部有 `kind: "monitor"`,不进 SDK 消息)。适配器按 `task_started` 的 `tool_use_id` 查它是哪个工具,是 `Monitor` 就报 `monitor`。CLI 里另有 `monitor_mcp`、`monitor_ws`、`local_workflow`,按名字归类即可。
- **空闲回收**:任务在跑时进程不释放;`idleMs` 1 秒,任务跑约 10 秒,都以 `completed` 结束,没有 `stopped`。
- **goal**:本地进程**收不到** `active_goal`。CLI 只在设了 `CLAUDE_CODE_REMOTE`(云端容器)时才把它写进 SDK 输出;设了它时生命周期和 protocol.md 一致(设定时 `iterations` 0,没达成每次加 1 并带 `last_reason`,达成时 `null`)。适配器不设这个变量(它还会改登录、子 agent 并发、可用的工具),也不读 CLI 的会话记录,见 [决定笔记](../../.agents/notes/2026-11-22-claude-goal-not-supported.md)。真实模型测试里的 goal 用例收不到时只打印"未送达",收到时才断言,跟进见 CYCL-121。

### 隔离登录验证

2026-11-20（CYCL-110），用临时 HOME、Claude 配置和工作目录运行官方 CLI。初始 `auth status --json` 返回 `loggedIn: false`、`authMethod: "none"`。`claude auth login --claudeai` 打开了浏览器授权流程；按本轮验收范围在用户授权前停止。另用临时 Cycle 数据目录运行 `cycle claude auth status --json`，宿主环境中的模拟 OAuth、API 和 SSO 凭证均未使 Claude 进入登录态。单元测试检查了实际传给 Claude 的环境白名单、HOME 和配置路径。

待验证的是在隔离目录完成账号授权后，经 Cycle 创建会话并完成一个模型回合。已有的显式 token 模型测试覆盖另一条凭证路径。
