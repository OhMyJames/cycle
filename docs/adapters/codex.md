# Codex 适配

状态:定稿。真实模型验证日期 2026-11-23。

`harness/codex`:对 daemon 说 ACP v2,对下驱动随 Cycle 分发、固定版本的 `codex app-server`(stdio 上的 JSON-RPC)。一个适配器进程下面一个 app-server 进程,一个 session 一个 thread。登录隔离在 `CODEX_HOME=<数据目录>/codex`。为什么这样接,见文末的附录"初始调研"。

验证所用版本:**Codex CLI/app-server 0.171.0**,`@agentclientprotocol/sdk` 2.7.0,Bun 1.4.4。真实模型是账号的默认模型 `gpt-6.2-sol`(ChatGPT Pro 账号),effort `low`。

## 二进制和升级

构建时由 Bun lockfile 校验官方 npm 平台包,从中取原生 CLI。发行物运行时不需要 Node 或 npm。daemon 安装目录和桌面包的 `bin` 下都有 `codex`;Linux 还带同版本的 `codex-resources/bwrap`。许可随 `codex-resources/licenses` 一起安装。

升级步骤:核对 npm 的 latest 与 GitHub 正式 release,在 `harness/codex/package.json` 更新精确版本并 `bun install`;`bun harness/codex/scripts/generate.ts` 重新提取这一版的协议类型;核对 `harness/codex/src/protocol.ts` 的通知 allowlist;跑 `bun run format`、`bun run check`、`bun run test:integration`,再跑一次两份 `test:real`(见下);在各目标平台从安装目录跑 Codex 集成套件,复核沙箱、包体积和上游许可。

## 启动与配置

- 入口 `cycle adapter codex`。配置经 `CYCLE_ADAPTER_CONFIG`:`{ env, codexExecutable? }`。`env` 是 app-server 能看到的**全部**环境,必须有绝对路径的 `HOME` 和 `CODEX_HOME`;daemon 按 `config.json` 的 `codex` 段填(白名单 `allowEnv` 加 `env`,`HOME` 不传、回落到 `CODEX_HOME`)。
- app-server 一律带 `-c cli_auth_credentials_store="file"`(登录只在 `$CODEX_HOME/auth.json`,不进钥匙串)和 `-c check_for_update_on_startup=false`;`initialize` 声明 `experimentalApi: true`(plan 模式要用)。
- Cycle 要的设置一律经 `thread/start`、`thread/resume` 的参数和 `config` 传,不写 `$CODEX_HOME/config.toml`(那个文件归用户)。

## 登录

- `cycle login codex`(参数原样传给 `codex login`,如 `--device-auth`、`--with-api-key`)和 `cycle codex <参数>` 在 daemon 那台机器上,用 daemon 给 Codex 的同一份环境跑 Codex 自己的命令行。`CODEX_HOME` 还不存在时先建好(0700):Codex 不肯在一个不存在的 `CODEX_HOME` 上登录或查状态(实测,全新数据目录里原先直接报错退出)。
- 回合因 `codexErrorInfo: "unauthorized"` 失败时,错误说"先在 daemon 那台机器上跑 `cycle login codex`"。
- 远端:在远端跑 `cycle login codex --device-auth`(设备码,要先在 ChatGPT 的安全设置里打开),或把一份 `auth.json` 放进远端的 `<数据目录>/codex/`。本机和远端的步骤写在 [daemon.md](../daemon.md)。
- **一份 ChatGPT 登录不要同时给两个 Codex 用**:access token 由持有它的那个 Codex 刷新,刷新会换掉 refresh token,另一份就失效了。所以 Cycle 用自己的 `<数据目录>/codex`,不读 `~/.codex`;从 `~/.codex` 拷一份过来能用(实测),但之后两边会互相挤掉。

### 权限模式

| 值            | 界面上的名字                 | 说明(原文)                                             | `approvalPolicy` | 沙箱                 | 其他                               |
| ------------- | ---------------------------- | ------------------------------------------------------ | ---------------- | -------------------- | ---------------------------------- |
| `default`     | Ask when leaving the sandbox | Write in the workspace and ask before going beyond it. | `on-request`     | `workspace-write`    | —                                  |
| `untrusted`   | Ask before commands          | Ask before running commands outside the trusted set.   | `untrusted`      | `workspace-write`    | —                                  |
| `read-only`   | Read only                    | Read files and ask before making changes.              | `on-request`     | `read-only`          | —                                  |
| `auto-review` | Auto review                  | Let Codex review requests to go beyond the sandbox.    | `on-request`     | `workspace-write`    | `approvalsReviewer: "auto_review"` |
| `plan`        | Plan mode                    | Create a plan and wait before making changes.          | `on-request`     | `workspace-write`    | `collaborationMode: plan`          |
| `full-access` | Full access                  | Run without sandbox restrictions or approval prompts.  | `never`          | `danger-full-access` | `cycle/danger`                     |

在 `workspace-write` 相关档位(`default`、`untrusted`、`auto-review`、`plan`)下,当 `denyRead` 非空或 `<cwd>/.agents` 为真实目录(非符号链接)时,线程通过 `config.default_permissions = "cycle"` 启用继承 `:workspace` 的权限档案(且不在线程级再传 `sandbox`,否则 Codex 会忽略该档案):仅放行 `<realpath(cwd)>/.agents/worktree` 与 `<realpath(cwd)>/.agents/notes` 的写权限(跳过符号链接),保留 `.agents/skills`、`.git`、`.codex`、`.aws` 的只读保护,并把 `denyRead`(`secrets.env`、`providers.json`)设为 `none`。Linux 下 `denyRead` 只传入已存在的文件,避免 bubblewrap 为不存在的 `none` 目标在宿主机建出 0 字节挂载点。详见 [决定笔记](../../.agents/notes/2026-11-24-codex-agents-worktree-and-notes-sandbox.md)。

### 子 agent

实测(真实模型,0.171.0 默认的 multi-agent v2):

- 模型起子 agent 时,父线程里来的是 **`subAgentActivity`** item(`kind: "started"`,带子线程的 `agentThreadId` 和 `agentPath`,如 `/root/pong_agent`),**不是**类型里那个带 `receiverThreadIds` 的 `collabAgentToolCall spawnAgent`。父线程里的 `collabAgentToolCall` 只有 `wait`,`receiverThreadIds` 为空。子 agent 结束时父线程里再来一个 `kind: "completed"` 的 `subAgentActivity`。
- 子线程的事件(`turn/started`、item、`turn/completed`、token 用量)自动推给同一个连接,不用订阅;子线程没有 `thread/started`。
- 子线程里的审批请求带子线程的 `threadId` 和子线程自己的 `turnId`。

适配器的做法:`subAgentActivity started` → 在父 session 里发 `subagent_update`(`running`,标题取 `agentPath` 的最后一段,`capabilities.cancel`,`_meta["cycle/subagent"].toolCallId` 指向同一个 item 画成的 `spawn_agent` 工具调用;子 agent 再起的子 agent 带 `parentId`)。子线程的对话以子线程 id 为 `sessionId` 发出,daemon 转成 `_cycle/child_update`。子线程的 `turn/started` → `running`,`turn/completed` → `idle` 加对应的 `stopReason`;`interrupted` 的活动 → `idle cancelled`。停一个子 agent = 对它自己线程、自己的回合 `turn/interrupt`,父回合照常。子 agent 的审批和提问随它自己的回合结束(结束、被停)而收回,daemon 那边同时结清。v1 工具那种 `collabAgentToolCall` 的 `receiverThreadIds` 和 `agentsStates` 也照样认。

### 审批里的 `availableDecisions`

请求里(实验字段)列出 Codex 接受的回答。要跑出沙箱的命令只列 `accept`、`acceptWithExecpolicyAmendment`、`cancel`,没有 `decline`。实测:回 `decline` 它照收,命令不跑,模型接着说完("Refused."),回合正常结束;回 `cancel` 则整个回合以取消结束。所以拒绝一律回 `decline`。

## 自带模型(CYC-300)

Codex 只会说 Responses API。主人自己的模型服务(Anthropic、Google、OpenRouter 等 pi-ai 认识的,或任何 OpenAI/Anthropic 兼容端点)经 daemon 里的回环网关(`packages/model-gateway`,用 pi-ai)交给 Codex。决定和理由见 [决定笔记](../../.agents/notes/2026-11-24-codex-own-models-through-a-pi-ai-gateway.md)。

- 服务商存在 `<数据目录>/providers.json`(0600,含 key)。协议里没有任何答复带 key,只有 `hasKey`。方法:`_cycle/providers/{list,catalog,save,remove}`,变化时广播 `_cycle/providers_changed`。
- 模型叫 `<服务商 id>/<模型 id>`。daemon 把它们加进 codex 的 `model` 选项(`_meta["cycle/provider"]` 标出服务商),不进选项缓存。
- **一个 session 要么在 Codex 自己的模型上,要么在主人的模型上**,由它开始时的模型决定:daemon 在 `session/new`、`session/resume` 的 `_meta["cycle/model"]` 里告诉适配器。适配器用线程自己的 `config` 把网关设为 model provider(不写 `config.toml`),网关令牌只在 app-server 的环境里,并用 `shell_environment_policy.exclude` 挡住命令。session 里的模型菜单只列同一种,另一种被拒绝。
- **模型元数据走线程自己的 `model_catalog_json`。** Codex 0.171.0 对不认识的模型用 272K fallback,并且会把 `model_context_window` 也裁到 272K;只传窗口得不到 1M。适配器为这个 session 的全部主人模型写一份临时 catalog,每项带真实 `context_window`、`max_context_window`、该服务商支持的 effort,并开启 `supports_search_tool: true`(与随包模型一致,避免 Codex 把全部 MCP / `codex_apps` 工具直接铺进首轮请求导致上下文暴涨,改为按需走 `tool_search`,网关同时过滤 `request.tools` 中带 `defer_loading: true` 的工具);指令模板取自随包 Codex 的 `debug models --bundled` 里 `gpt-5.6-sol` 的条目。`effective_context_window_percent` 是 95,所以 1M 模型在状态里报 950000,64K 模型报 60800。临时目录 0700、文件 0600,随 session 关闭、打开失败或 app-server 结束删除;Codex 自己的模型不生成 catalog。
- **DeepSeek 的 catalog 还有一组自己的优化。** 按 DeepSeek 的 Codex 集成启用 freeform `apply_patch`、verbosity 支持(默认 `high`;Codex 0.171.0 的枚举只有 `low`、`medium`、`high`)和 `supports_parallel_tool_calls: true`。自动压缩阈值是 500000,且不会超过该模型 95% 有效窗口。Codex 0.171.0 的 `debug models` 会把未知 catalog 里的 `supports_parallel_tool_calls` 读回为 null;字段先随着官方 catalog 保留,但当前版本是否真正开启并行调用还没有验证。
- **mixed code mode 实测后不采用。** 同一组真实 DeepSeek 任务各跑 3 次:direct 平均 4 次模型请求、7 次工具调用、34822 cumulative input、3/3 成功;`code_mode` 平均 5 次模型请求、5 次工具调用、54735 cumulative input、3/3 成功。它减少了工具调用,却增加了模型往返和上下文重放,所以 DeepSeek 继续用 direct tools,也不进入 `code_mode_only`。复现脚本是 `apps/daemon/scripts/codex-deepseek-ab.ts`。
- 网关只回答本次 daemon 启动时生成的令牌,第一次有 session 用到才起,daemon 关闭时停。

没有验证:任何真实的服务商、打包后的桌面应用。已知限制:DeepSeek 之外不认识的模型仍拿不到 `apply_patch`;网页搜索和图片生成是 OpenAI 的服务端工具,都用不了;Gemini 的 thoughtSignature 只在内存里,daemon 重启后丢。

## 未做(显式列出,不要悄悄补)

- "以后不问这类命令"(`acceptForSession`、`acceptWithExecpolicyAmendment`)这类审批选项:只给允许一次、拒绝一次。
- goal(`thread/goal/*`)、后台终端、`/review`、Fast 档(`serviceTier`)、从桌面端发起登录(`account/login/start`)。
- **plugin**(protocol.md §15,`harness/codex/src/plugins.ts`):`CodexPlugins` 在 daemon 私有的 `CODEX_HOME` 下运行 `codex plugin list|add|remove|marketplace … --json`。`codex plugin` 没有启停命令,开关是 `config.toml` 的 `[plugins."<id>"] enabled`,只改这一行。`ensureBuiltin` 装随 Cycle 发的 plugin(`packages/clawdot-plugins`,见笔记 2026-11-24-builtin-plugins-are-installed-by-cycle)。plugin 自带的 MCP 服务器没有接网关,都标 `by: "agent"`。
- `isSecret` 的问题没有单独处理:表单答案本来就不进日志(protocol.md §9)。
- 沙箱拦下的工作区外写入,app-server 不发对应的 `commandExecution` item(容器里实测;模型看得到失败,客户端看不到这条命令)。是 Codex 的行为,适配器补不出来。
- 长会话的内存没测(一个 session 是适配器加 app-server 两个进程)。

## Linux 沙箱(CYCL-208,2026-11-23)

Linux 上 Codex 用 bubblewrap 隔离命令(随包带 `codex-resources/bwrap`;系统 PATH 上没有 bwrap 时 app-server 记一条 ERROR 并发 `configWarning`,然后用随包的那份)。在 OrbStack 的 Docker(arm64)里,用真实模型、`workspace-write` 加 `on-request` 跑"工作区里写文件、工作区外 `touch`、`curl`"三条命令:

| 环境                                                                            | 工作区里写 | 工作区外写                    | 联网               | 结论                                                    |
| ------------------------------------------------------------------------------- | ---------- | ----------------------------- | ------------------ | ------------------------------------------------------- |
| Debian bookworm,Docker 默认                                                     | 失败       | 失败                          | 失败               | 沙箱起不来,三条都以 bwrap 的报错失败,exit 1             |
| Ubuntu 24.04,Docker 默认                                                        | 失败       | 失败                          | 失败               | 同上                                                    |
| bookworm,`--security-opt seccomp=unconfined --security-opt apparmor=unconfined` | 成功       | 被拦("Read-only file system") | 被拦(解析不了域名) | 沙箱和 macOS 上一样工作;要跑出沙箱时照常审批,批准后成功 |
| bookworm,Docker 默认,`full-access`                                              | 成功       | 成功                          | 成功               | 不隔离,能用                                             |

- 起不来时的报错(命令的输出里):`bwrap: No permissions to create a new namespace, likely because the kernel does not allow non-privileged user namespaces. On e.g. debian this can be enabled with 'sysctl kernel.unprivileged_userns_clone=1'.` 在容器里提示的 sysctl 不是原因,原因是 Docker 默认的 seccomp/AppArmor 配置。
- **Codex 不会自己退到不隔离**,也不会因为沙箱起不来而主动审批:失败作为普通的失败命令回给模型。只有模型自己要求提权("May I rerun … with escalated permissions because the sandbox failed to start?")才会来审批,批准后不经沙箱跑。也就是说在这种环境里 `workspace-write` 下每条命令都要人批,而且取决于模型想不想问。
- **退路**:适配器不自动降档(红线:不悄悄扩大权限)。看到这个报错时在会话里发一条提示,给两条路:让 Cycle 跑在允许非特权用户命名空间的地方(容器加上面两个 `--security-opt`,或宿主机打开 user namespace),或者用户自己选 Full access。
- 一台真正的远端 Linux 主机没跑:按上表,决定因素是能不能创建用户命名空间,宿主机上默认能(Ubuntu 24.04 宿主机受 AppArmor 限制时要按 OpenAI 的 [Linux sandbox prerequisites](https://learn.chatgpt.com/docs/sandboxing#prerequisites) 装发行版的 bubblewrap 并加载它的 profile)。第一阶段已在 Debian 12 ARM64 上验证过安装布局能执行工作区命令、工作区外写入被拒。

## 真实模型验证(2026-11-23)

测试:`harness/codex` 下 `CYCLE_CODEX_AUTH=<auth.json> bun run test:real`(适配器层,6 条),`apps/daemon` 下 `CYCLE_CODEX_AUTH=<auth.json> bun run test:real:codex`(经过 daemon,中间重启它);另用直接驱动 app-server 的探针看原样的事件。登录文件每条测试拷进自己的临时 `CODEX_HOME`,给的那份只读;整轮下来 `auth.json` 没被刷新。见 [testing.md](../testing.md)。

| 问题                             | 结果                                                                                                                                                                                                           |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 流式回答                         | 通过。一个单词的回答约 4.6 秒,`end_turn`                                                                                                                                                                       |

### 选 app-server,自己写适配

理由:

1. **它是唯一同时有审批、插入、恢复、子 agent 的入口**,而这四样正是 Cycle 协议里已有、Claude 已经做了的(§4 逐项对上)。`exec --json` 和 SDK 缺前两样。
2. **AGENTS.md 的约束对 Codex 同样成立**:适配自己写、自包含、传输可替换。适配器进程只做一件事:一头是 ACP v2(stdio),一头是 app-server 的 JSON-RPC(子进程的 stdio)。不需要 Node,不引入 npm 上的 Codex 包,类型从固定版本的 `generate-ts` 产物来。
3. **翻译量小于 Claude**:app-server 的模型(thread、turn、item,带 started/delta/completed)和 ACP v2 的形状很近,审批本来就是服务端发起的请求,子 agent 本来就是带 `parentThreadId` 的线程。【实测 + 类型】

### 为什么不用 codex-acp

- 它在 Cycle 需要的每个扩展点上都是别的约定:插入用它自己的 `_session/steering`(我们是 `session/prompt` 的 `_meta["cycle/steer"]`);不认 `cycle/sessionId`、`cycle/hadTurn`、`cycle/trusted`;工具结果没有 `cycle/toolResult`;恢复文档里只提 `session/load`(重放),而我们要的是不重放的 `session/resume`。【文档:它的 README】要么改它,要么在 daemon 里为它写一层补丁,后者正是 AGENTS.md 说不要照搬的东西。
- 它依赖 `@agentclientprotocol/sdk ~2.9.1`,我们固定在 2.7.0;它带的 Codex 版本由它的发布节奏决定。两个版本都不在我们手里。
- 它是 Node 包,而 Cycle 的发行物是一个 Bun 单文件加各 agent 的二进制。
- 这和 0001 决定(不用官方 `claude-agent-acp`)是同一个判断。**但它值得读**:同样是 app-server → ACP v2 的翻译,Apache-2.0,踩过的坑(子 session、审批选项、斜杠命令怎么凑)可以取"为什么",不取实现。

### 进程模型

- 一个适配器进程下面一个 `codex app-server` 进程。app-server 本身是多线程(thread)的,一个进程能带多个会话;Cycle 现在是一个 session 一个适配器进程,先照这个来,不为 Codex 另做共享。
- 很轻:`initialize` 0.17 秒返回,进程 57 MB;开 3 个空线程后 87 MB,没有子进程。【实测,空闲、没跑过模型】对比 Claude 一个空闲进程约 230 MB。所以 **v1 不做空闲释放**(Claude 的决策 0007 是被内存逼出来的),适配器在,app-server 就在;daemon 自己的空闲回收(`agent_reclaimed`)照常整个收走。跑过长会话之后的内存没测,测了再决定。
- 握手:`initialize`(`clientInfo`,`capabilities.experimentalApi: true`),再发 `initialized` 通知。【实测】

## 2. 安装和登录

### 二进制:随 Cycle 分发,固定版本

**随 Cycle 带,不用机器上的。** 理由不是方便,而是 app-server 的协议按版本变,适配器是对着某一个版本的类型写的;机器上的 `codex` 会被用户、ChatGPT 桌面端、`codex update` 随时换掉(本机就同时有两份:`~/.local/bin/codex` 0.166.0 和 ChatGPT.app 里自带的一份)。Claude 也是带着走的。`config.json` 的 `codex.executable` 留一个覆盖口子(和 `claudeExecutable` 一样),给想用自己那份的人,不保证能用。

**许可**:Apache-2.0【实查 GitHub API `repos/openai/codex/license`】,可以再分发,要带上许可和 NOTICE。

**大小**(0.171.0 的发布资产,十进制 MB【实查 GitHub API `releases/latest`】;解包后的数字来自本机 0.166.0【实测】):

| 资产                                                | macOS arm64 | Linux x64 (musl) | Linux arm64 (musl) | 说明                                                                                   |
| --------------------------------------------------- | ----------: | ---------------: | -----------------: | -------------------------------------------------------------------------------------- |
| `codex-<target>.tar.gz`(完整命令行一个文件)         |         117 |                — |                124 | 解包 269 MB(本机 0.166.0 的 `bin/codex`)                                               |
| `codex-app-server-<target>.tar.gz`(只有 app-server) |          91 |               94 |                 96 | 解包大小没量                                                                           |
| `codex-package-<target>.tar.gz`(完整目录)           |         176 |                — |                199 | 本机解包 407 MB:`codex` 269、`codex-code-mode-host` 69、`codex-exec-server` 63、`rg` 4 |

Cycle 的包现在是压缩 222 MB、解包 484 MB(docs/daemon.md),加上 Codex 约多 **90–120 MB 压缩、约 270 MB 解包**(只带一个文件时)。

带哪一个,没定,第一个子任务要回答:

- 只带 `codex` 一个文件最省事:`codex app-server`、`codex login`、`codex plugin` 都在里面,`cycle codex <参数>` 直接可用。离开同目录的 `codex-code-mode-host` 不行:模型开 code mode 时,工具调用都经 `exec` 在这个宿主里跑,缺了它每个调用都报 `failed to spawn code-mode host`,也不会有 `commandExecution` item(2026-11-24 打包的应用里实测)。所以它和 `codex` 一起带(harness 的 `companions`)。`codex-exec-server`、`rg` 缺了还没见到问题。
- 只带 `codex-app-server` 更小,但没有 `codex login`,登录要改走 app-server 的 `account/login/start`(见下)。
- Linux 的资产是 musl 静态构建,x64 和 arm64 都有,所以远端机器不挑发行版。【实查资产名】发布里另有单独的 `bwrap-<target>`(Linux 沙箱用)。实现随 Linux 包带了同版本的 `codex-resources/bwrap`,系统没有 bwrap 时 Codex 用它【实测,容器里】。

**不能让它自己升级**:`features list` 里有 `in_app_updates`(stable/true),命令里有 `codex update`。【实测】随包的二进制被换掉,适配器就对不上了。启动时要关掉(`--disable in_app_updates` 或对应配置),关得掉没验证。

### 登录隔离:`CODEX_HOME`

- `CODEX_HOME` 默认 `~/.codex`,凭证、配置(`config.toml`)、会话记录(`sessions/`)、技能、插件、几个 SQLite 都在里面。【文档 <https://learn.chatgpt.com/docs/auth.md>;实测目录内容】
- **隔离成立**:`CODEX_HOME` 和 `HOME` 指向临时目录、其余环境为空时,`initialize` 回报 `codexHome` 是那个目录,`account/read` 返回 `account: null, requiresOpenaiAuth: true`,`codex login status` 报 "Not logged in";同一台机器的 `~/.codex/auth.json` 存在(只看了文件在不在,没读)。跑完之后它写的所有东西都在临时目录里。【实测】
- daemon 给的是 `CODEX_HOME=<数据目录>/codex`(`config.json` 的 `codex.configDir` 可改),`HOME` 不传、回落到它,和 Claude 一样。
- **凭证必须落在文件里**:`cli_auth_credentials_store` 可以是 `file`(`$CODEX_HOME/auth.json`)、`keyring`(系统钥匙串)、`auto`、`ephemeral`。【文档 auth.md】钥匙串不在数据目录里,按什么键区分不同的 `CODEX_HOME` 没查。所以登录和启动都显式带 `-c cli_auth_credentials_store="file"`。Cycle 的 connector 不走 Codex 的 MCP OAuth,所以 MCP 的凭证存储不用管。
- **环境变量**(红线:不继承)。实测跑命令时 Codex 给子进程的环境只有我们给的 `PATH`、`HOME`、`CODEX_HOME`,加它自己设的 `CODEX_*`、`LANG`、`TERM=dumb`、`NO_COLOR`、几个 `*_PAGER`;没有多出来的。【实测 `env > 文件`】所以白名单照 Claude 的做:`allowEnv` 点名的加 `env` 写明的。`OPENAI_API_KEY`、`CODEX_API_KEY` 在环境里时 app-server 会不会直接拿去用,**没验证**(codex-acp 的 README 说它自己读这两个;官方 auth 文档只把 `OPENAI_API_KEY` 当作 `codex login --with-api-key` 的输入)。白名单之下这只在用户自己写进 `codex.env` 时才有关系,那是他有意的。
- 注意:模型跑的命令能看到 `CODEX_HOME`,沙箱默认允许读整个磁盘,所以**命令读得到 `auth.json`**。Claude 的 `CLAUDE_CONFIG_DIR` 是同样的情况,不是新问题,但它是 Codex 自己的 token,不是 Cycle 账号的(红线"账号或 SSO 的 token 不得到达 agent"说的是后者)。

### `cycle login codex`

在 daemon 所在的机器上,用 daemon 给 Codex 的同一份环境跑 Codex 自己的登录(依赖 CYCL-155 的 `cycle login <agent>`):

| 方式                | 命令                                                                            | 适用                                                                        |
| ------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| ChatGPT 账号,浏览器 | `codex login`                                                                   | 本机。回调在 `localhost:1455`                                               |
| ChatGPT 账号,设备码 | `codex login --device-auth`                                                     | 没有浏览器的机器。文档标 beta,且要在 ChatGPT 的安全设置或工作区权限里先打开 |
| API key             | `printenv OPENAI_API_KEY \| codex login --with-api-key`(从 stdin 读,不进命令行) | 按 API 价计费                                                               |
| access token        | `codex login --with-access-token`(stdin)                                        | 文档有,没细看                                                               |

【文档 auth.md;实测 `codex login --help` 里这三个参数都在】登录流程本身没走过(要账号)。

以后要从桌面端发起登录,app-server 有 `account/login/start`:`chatgptDeviceCode` 返回 `verificationUrl` 和 `userCode`,`chatgpt` 返回 `authUrl`,完成时发 `account/login/completed`。【类型 + 文档 app-server.md】这不在首批范围里。

**条款风险(要负责人确认,不是工程问题)**:app-server 文档的认证一节写着 "App-server authentication has never been permitted for commercial or hosted services",并说本地或开源应用可以继续用、建议迁到 "Sign in with ChatGPT"(有合作方候补名单)。【文档 app-server.md】Cycle 是跑在用户自己机器上、用用户自己 Codex 登录的应用,我读下来属于"本地应用"那一类;但 Cycle 是不是"commercial service",以及用 `codex login`(命令行自己的登录)再起 app-server 算不算这句话说的情况,我判断不了。API key 登录不受这句话影响。

### 远程环境(daemon 在 ssh 那一头)

daemon、适配器、Codex 都在远端,所以二进制和登录都在远端:

- 二进制随那个平台的 Cycle 包走(Linux musl,x64/arm64 都有)。
- 登录在远端做,文档给了三条路:设备码(首选);`ssh -L 1455:localhost:1455` 之后在那个会话里跑 `codex login`;或者把一份 `auth.json` 拷过去。【文档 auth.md】Cycle 这边对应的是在远端跑 `cycle login codex --device-auth`(参数原样传给 `codex login`),或者把 API key 写进远端 `config.json` 的 `codex.env`(前提是上面"环境变量"那条验证通过,否则用 `--with-api-key`)。
- **Linux 沙箱**:Codex 在 Linux 上用 bubblewrap 隔离命令,Docker 默认配置下起不来,每条命令都失败【实测】。结论和退路见上文"Linux 沙箱"。

## 3. 会话

- Codex 的会话叫 thread。id 由 Codex 生成,UUIDv7;记录是 `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<时间>-<threadId>.jsonl`。【实测】路径里没有 cwd。
- **不能采用 daemon 提议的 id**:`thread/start` 的参数里没有 id(稳定和 experimental 两份类型都没有);硬塞一个 `threadId` 被忽略,照样生成自己的。【实测】所以按 protocol.md §6 是**关联**:适配器在 `NewSessionResponse` 里返回 thread id,daemon 记成 `agentSessionId`。
- **恢复**:新进程里 `thread/resume {threadId, excludeTurns: true}`,再 `turn/start`,发给模型的请求里带着上一个进程里的全部对话(用户消息、工具调用和结果、插入的那条)。【实测,模拟模型】`excludeTurns` 让它不把历史回给我们,正好是"不带 `replayFrom`"。`thread/resume` 同样接受 `model`、`approvalPolicy`、`sandbox`、`config`、`developerInstructions`,所以 daemon 重发的配置、`mcpServers`、系统提示有地方放。【类型】
- **没有过回合的线程没有记录,这里和协议有一处对不上**:`thread/start` 之后、第一个回合之前,磁盘上没有 rollout;换一个进程 `thread/resume` 得到 `-32600 no rollout found for thread id …`。【实测】对应 §7 的"没找到且没有 `cycle/hadTurn`:当新的开始(用同一个 id)",但 Codex 不能用同一个 id 重新开始,新线程是新 id。两种解法,要在"会话"那个子任务里定一个:
  - **A(建议)**:允许 agent 在 `session/resume` 的应答里用 `_meta["cycle/agentSessionId"]` 报一个新的 agent 侧 id,daemon 把索引里的 `agentSessionId` 换成它。对应关系仍然只有索引这一处。要先改 protocol.md §6/§7(对客户端不可见,`sessionId` 不变)。
  - B:适配器对 daemon 一律采用 `cycle/sessionId`(看上去是"复用"),自己在 `$CODEX_HOME` 里存 `sessionId → threadId`。不用改协议,但多了一份会和索引不一致的状态。
  - 有 `cycle/hadTurn` 而找不到 rollout:照协议回错误(`resume_failed`)。
- 回合失败(比如没登录)时 rollout 写没写,没测;两种情况上面的规则都能接住。
- `thread/list`、`thread/archive`、`thread/delete`、`thread/fork` 都有【类型】,不用:daemon 自己管列表和历史。删除 session 时要不要顺手 `thread/delete` 掉 Codex 那份记录,和 Claude 现在的做法保持一致即可。

## 5. 配置项

### `configSchema`(给客户端画表单,`cycle/config` 的键)

和 Claude 用同样的三个键,客户端不用认新东西。

**`mode`**(Permission mode):Codex 没有单一的权限枚举,它是"审批策略 × 沙箱 × 谁来审"。组合起来给人选,值是 Cycle 起的名字,每个值对应的 Codex 原值写死在适配器一处(`CODEX_PERMISSION_MODES`,同 `CLAUDE_PERMISSION_MODES`),`configOptions` 和 `configSchema` 都从它生成:

| 值            | 名字                         | `approvalPolicy` | `sandbox`            | 其他                               | 标记                                            |
| ------------- | ---------------------------- | ---------------- | -------------------- | ---------------------------------- | ----------------------------------------------- |
| `default`     | Ask when leaving the sandbox | `on-request`     | `workspace-write`    | —                                  | 默认(Codex 自己对受信任项目的默认)              |
| `auto-review` | Auto review                  | `on-request`     | `workspace-write`    | `approvalsReviewer: "auto_review"` | 候选的 `cycle/recommended`,等真实账号上试过再定 |
| `untrusted`   | Ask before commands          | `untrusted`      | `workspace-write`    | —                                  | 实测:连 `sleep 3` 都问                          |
| `read-only`   | Read only                    | `on-request`     | `read-only`          | —                                  | —                                               |
| `plan`        | Plan mode                    | 不变             | 不变                 | `collaborationMode: plan`          | 见 §4;放不放进 `mode` 见 §6                     |

英文说明(界面上显示的原文)在实现时写,照 claude.md 那张表的写法:说清选了会怎样。运行中切换:下一个 `turn/start` 带上新的 `approvalPolicy`、`sandboxPolicy`(对之后的回合都生效),或 experimental 的 `thread/settings/update`;Codex 自己改了设置时有 `thread/settings/updated`,转成 `config_option_update`。【类型;通知实测见过】

**`model`**:`oneOf` 来自 `model/list`(`id`、`displayName`、`description`),加一项 `default`(不传,由 Codex 按 `config.toml` 和账号决定);`_meta["cycle/open"]: true`。进程起来之前没有清单,这时只有 `default`,和 Claude"进程还没报清单"时的处理一样;daemon 的清单缓存补上其余的。

**`effort`**:`default`(不覆盖)加当前模型的 `supportedReasoningEfforts`;每个模型可选的档位放在模型选项的 `_meta["cycle/efforts"]`。换模型后旧档位不支持就改回 `default`。

不放进首批的:`serviceTier`(清单里每个模型有 `serviceTiers`,实测是一档 "Fast: 2x speed, increased usage")、思考摘要的详略、联网搜索开关、`multiAgentMode`。

### `config.json` 的 `codex` 一节(daemon 的配置,不经协议修改)

CYCL-155 的"每个 agent 一个顶层键":

```json
{
  "codex": {
    "configDir": "/path/to/codex-home",
    "allowEnv": ["PATH", "LANG", "LC_ALL", "TERM"],
    "env": {},
    "executable": "/path/to/codex"
  }
}
```

- `configDir`:就是 `CODEX_HOME`,默认 `<数据目录>/codex`。里面的 `config.toml` 归用户(想要的 MCP 服务器、默认模型写在这里);Cycle 必须要的设置一律走启动参数 `-c` 或 `thread/start.config`,不写这个文件。
- `allowEnv`、`env`:同 Claude。`HOME` 不传,回落到 `configDir`。
- `executable`:不写就用随包的那份。
- 适配器的启动配置照旧经 `CYCLE_ADAPTER_CONFIG`:`{ env, codexExecutable? }`。

## 6. 待定和风险

要负责人定的:

1. **条款**(仍待负责人定):§2 那句 "App-server authentication has never been permitted for commercial or hosted services" 适不适用于 Cycle。
2. **包的大小**:多 90–120 MB(压缩)能不能接受;不能的话是首次使用时再下载,那是另一套机制。
3. **plan 模式怎么退出**(§4):已按"不模拟"做,`plan` 放在 `mode` 里。
4. **会话 id 的解法 A 还是 B**(§3):已按 A 做(`cycle/agentSessionId`)。

工程上的风险:

- **协议跟着版本变**,而且我们要用的一部分在 `experimentalApi` 后面。当前基线是 0.171.0，类型来自该版本的 `generate-ts`，适配器只消费 `harness/codex/src/protocol.ts` 列出的通知。升级 Codex 是一次有测试把关的改动，必须重新生成类型、核对通知 allowlist，并跑完整回归。
- **Linux 沙箱**:已在容器里验证,结论和退路见上文"Linux 沙箱"。
- **自动升级**关不关得掉(§2)。
- **真实模型**:已验证,见上文"真实模型验证"。
- 一个 session 两个进程(适配器 + app-server)再加模型跑的命令;长会话的内存没测。
- Windows 没看(Cycle 现在也不发 Windows 版)。
