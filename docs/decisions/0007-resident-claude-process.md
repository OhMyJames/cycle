# 0007 每个 session 一个常驻的 Claude 进程,空闲时释放

状态:已接受(2026-11-18)

## 决定

适配器为一个 session 起一个 Claude 进程(Agent SDK 的流式输入模式),这个 session 的 prompt 依次推进它的输入流,而不是每个回合起一个新进程。

- 进程在第一个 prompt 时启动:第一次用 `sessionId` 创建,之后(进程被释放或死掉之后)用 `resume`。
- 回合的结尾仍是一条 idle 的 `state_update`,由进程的 `result` 消息触发。
- 取消是 `interrupt()`:回合以 `error_during_execution` 的 result 结束,进程留着,session 继续。如果 3 秒内没有 result,杀掉进程,回合按 `cancelled` 结束,下一个 prompt 重新起一个。取消同时中止还在等答案的权限请求。
- `mode`、`model` 在进程运行时用 `setPermissionMode`、`setModel` 发给它;发不出去(进程已不在)就释放进程,下一个进程带着新的选项起来。
- 进程死了(流报错或结束):正在跑的回合以 error 结束,不自动重试;下一个 prompt 重新起一个。
- **空闲 5 分钟(`idleMs`)释放**:先结束输入让它自己退出,2 秒后仍在就中止。下一个 prompt 付一次启动的钱。
  - 两种情况不释放。一是有后台工作在跑(后台子 agent、后台命令或 Monitor),否则它们会随进程一起被杀。二是一小时内有定时调用要触发(CronCreate、ScheduleWakeup、/loop,读自每个回合结束时 Stop hook 的 `session_crons`):它们只在进程内存里,进程不在时到点的那次会丢失,resume 后也不补(CYCL-145,[笔记](../../.agents/notes/2026-11-23-keep-the-process-for-crons-due-within-the-hour.md))。

## 原因

每个回合起一个进程,在真实模型上单词回答是 2.7 秒,同一个进程里的后续回合是 1.5 秒,省约 1.2 秒。每个回合都付这笔钱,对一个对话式界面是明显的。

## 代价和为什么可以接受

- **内存**:一个空闲的 Claude 进程约 230 MB(实测),按打开的 session 数增长。目标机器是 2 核 4 GB,所以必须有空闲释放;5 分钟是在"连续对话不重启"和"别占着内存"之间的折中,可以配(`AdapterConfig.idleMs`)。
- **状态多了**:进程的生死、一个回合和进程的归属、取消的超时。这些都有单元测试(死在回合之间、死在回合中、空闲释放、释放后恢复、忽略 interrupt 的进程、取消时的权限请求)。
- **适配器重启后,session 的任务列表不记得之前的任务**:这和每回合一个进程时相同,不是新问题。

## 实测

- 适配器被 `kill -9` 后,它的 Claude 子进程随即退出(输入管道关闭),不会变成孤儿。
- `interrupt()` 在权限请求等待时也会中止它收到的 `signal`;适配器自己也把它和回合的取消连起来,不依赖这一点。
- 打断之后的下一条消息是干净的:没有被打断回合的残留事件。
- `system init` 每个回合都会再来一次。

## 为什么不是别的

- 保持每回合一个进程:简单,但每回合多 1 秒多。
- 进程永不释放:连续对话最快,但 N 个 session 占 N×230 MB,在 4 GB 机器上不可接受。
