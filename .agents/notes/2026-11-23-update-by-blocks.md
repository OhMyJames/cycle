# Agent Note: 差分更新细到文件内的 1 MiB 块,块单独压缩成一个发布资产

Status: accepted
Date: 2026-11-23
Basis: 2026-11-23 用户反馈:迁到 OhMyJames/cycle 之后每次更新都下整包。实测:Cycle-V1 上 0.3.13→0.3.14→0.3.15 每次变化 13–14%(只有 `bin/cycle`);0.3.15→0.3.16 起每次 93–95%,原因是同一提交(2cec427)换成了 Developer ID 签名加公证。签名带安全时间戳,每次发版所有 Mach-O 的字节都不同,即使代码没变。逐块比较 0.3.18 和 0.3.19:Electron Framework 197 块只差最后 1 块,`bin/claude` 339 块只差最后 2 块。

## Problem

按文件的差分([2026-11-18-update-by-the-difference](2026-11-18-update-by-the-difference.md))把"签名变了"当成"文件变了",要取的超过整包 80%,于是每次都退回整包(0.3.19 约 440 MB)。签名不能不带时间戳(公证要求)。

## Decision

- 发布时额外生成块包 `Cycle-<version>-<platform>-<arch>.blocks`:文件表里大于一个块(1 MiB)的文件按块切开,每块单独 raw deflate,依次拼接。清单加 `pack`:`file`、`size`、`blockSize`,和 `files`(路径 → 每块 `[sha256, offset, csize]`)。整包 zip 和文件表不变,没有这段代码的客户端照旧。
- 客户端对变了的大文件逐块比较已安装文件的块哈希:有的块从已安装文件复制,没有的用 Range 从块包取,解压后必须等于该块的 SHA-256;整个文件拼好后仍必须等于文件表的 SHA-256(信任链不变,块哈希只是更早发现坏块)。一个块都复用不了的文件仍从 zip 整个取。
- 块包不可用(清单里的块包不合格、release 里没有这个资产)只损失节省:变了的文件按原来的办法从 zip 取。块不符、解不开,和其他差分失败一样回退整包一次。
- 解析时限制块包:文件名必须是本版本的名字,只列文件表里大于一个块的文件,块数等于文件大小所需,每块在包内且压缩后不超过块大小的约 1.07 倍(一次请求最多攒 16 MiB)。

## Alternatives considered

- **复用上一版签好的二进制**(未签名内容相同就拿上一版已签名的字节):文件逐字节相同,按文件差分就够。但发布流水线要拉上一版的包、按嵌套顺序挑选性签名,签名和公证出错只能在发版时发现,而且客户端以外的路径没法在本机测。块级差分只动我们自己的打包和更新代码,能用真实的两个版本在本机验证。
- **在 zip 里用 deflate 全刷新点做可随机读取的块**:只有一个资产,但要自己写 zip 替代 `ditto`(AppleDouble、链接、权限),整包下载和安装的路径也跟着冒风险。
- **大文件在 zip 里不压缩**:整包下载变大好几百 MB。
- **按版本对生成二进制补丁(bsdiff 等)**:原来的笔记已经否决过,理由不变。

## Consequences

- 实测(真实的 0.3.18 已安装包 → 0.3.19,块包按本方案生成):不用块包时要取约 412 MB,超过阈值改下整包 440 MB;用块包时取 120 MB,15 个请求,拼出的包和文件表逐项一致。这 120 MB 里大部分是 0.3.19 新加的 `bin/codex`(这个文件是全新的,没法复用)。普通发版实测(0.3.19 → 0.3.20,只改了页面):不用块包时要取约 412 MB,于是改下整包 440 MB;用块包时只取 4.7 MB,13 个请求,复用了 917 个块。
- 每个 release 多一个约 430 MB 的资产(只占存储,用户只取需要的块);`release-assets` 多约 20 秒;清单多约 60 KB。
- 节省从包含这段代码的版本之后的那次更新开始;从更早的版本升级仍按文件差分或整包。
- macOS 集成测试(`update.integration.ts`)造的发布还没带块包,块路径只有单元测试和上面的真实数据验证。
